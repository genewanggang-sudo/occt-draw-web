# Onshape 点渲染问题定位与实现说明

## 目标

目标页面：

- `https://cad.onshape.com/documents/cb24420a26a5ed84801750a9/w/6afad649721589e7fdfade2a/e/86ba8a42171d7bde0922e59d`

本文目的不是继续做宽泛的“运行时分析记录”，而是回答下面三个更直接的问题：

1. 当前本地实现和 Onshape 的问题到底在哪里
2. Onshape 的点，底层实际上是如何实现的
3. 后续如果要对齐 Onshape，应该对齐哪些底层机制

当前阶段只做问题定位和实现说明，不修改任何实现代码。

## 结论先行

对于“点”这一条渲染路径，Onshape 不是简单的：

- `gl.POINTS + 纯圆点`
- `gl.POINTS + 贴图`
- `基础点 + 通用 halo 高亮`

而是至少拆成两条独立路径：

1. 基础点渲染路径
    - 以 procedural point-font shader 为核心
    - 主路径是 `billboard quad + fragment procedural glyph`
2. 点高亮路径
    - 单独的 highlight overlay/pass
    - 不复用基础点的 point-font 片元逻辑

这就是当前本地实现最核心的问题来源：

- 本地已经选择了 point-font 方向，这是对的
- 但本地还没有把“基础点”和“点高亮”拆成与 Onshape 同构的两条底层路径

## 当前本地实现的主要问题

只看草图点，当前本地实现相对 Onshape 至少有以下问题：

### 1. 点的抗锯齿语义仍不独立

Onshape 点使用独立的 `uPointFilterWidth`。

当前本地实现里，点仍然复用线的 `u_line_filter_width`。这会直接导致：

- 点边界覆盖宽度不对
- ring/空心点的过渡宽度不对
- 不同 DPR 下点的边缘观感不对

### 2. 点的 quad 外扩半径没有严格对齐

Onshape 基础点不是按“点半径本身”展开 quad，而是按：

- `vPointRadius + 0.5 * uPointFilterWidth * sqrt(2)`

也就是说，quad 展开半径里包含了给片元 AA 预留的边缘空间。

如果只按点半径展开，片元阶段虽然还能算 glyph，但边缘 AA 会被裁掉，最终视觉会偏硬、偏小，尤其是空心点更明显。

### 3. 点的最终颜色输出逻辑没有完全对齐

Onshape 基础点片元输出不是直接给 `pointColor`，而是：

- `mix(bgColor, pointColor, colorScale)`
- 然后再乘 `opacityScale`

这意味着：

- 点内部不同位置允许做背景混色
- ring 与空心区域不是简单 `discard / 不 discard`
- 视觉结果依赖背景色

如果本地直接输出实色或只做 alpha 裁切，结果会比 Onshape 更“死”。

### 4. 点高亮不是通用 halo

这是当前本地实现与 Onshape 差异最大的地方之一。

Onshape 点高亮不是“基础点外面套一圈放大的 halo”。运行时已经抓到它有独立的点高亮 shader：

- 独立 uniforms：
    - `uHighlightOpacity`
    - `uHighlightPointSizeMin`
    - `uHighlightPointSizeScale`
    - `uHighlightColor`
    - `uActiveHighlightIndex`
- 独立 attributes：
    - `aVertexPosition`
    - `aPointData`
    - `aPrimitiveSize`
    - `aHighlightId`

因此，高亮态至少具备这些独立语义：

- 是否参与当前高亮
- 高亮颜色
- 高亮透明度
- 高亮最小尺寸
- 高亮放大比例

本地现在的 halo 只是近似效果，不是同一实现。

### 5. 点语义分类不够细

Onshape 运行时和 bundle 常量都说明，点不是一类统一样式，而是至少区分：

- `sketch point`
- `sketch user point`
- `sketch spline handle point`
- `preview point`

同时还区分：

- active
- inactive
- hovered
- selected

当前本地如果只保留“普通点/顶点点”这种粗分类，底层 shader 数学就算对，最终表现仍然不会对。

## Onshape 的基础点是如何实现的

下面只说已经通过运行时抓到、能直接落到 shader 级别的事实。

### 1. 基础点主路径是 quad billboard，不是主用 gl.POINTS

运行时抓到的基础点 draw：

- `drawElements`
- `mode = 4`
- `count = 6`

也就是两个三角形拼成一个 quad。

这条路径的输入包括：

- attributes
    - `aVertexPosition`
    - `aVertexColor`
    - `aPointData`
    - `aPrimitiveSize`
    - `aPrimitiveStyle`
- uniforms
    - `uPointFilterWidth`
    - `uDevicePixelRatio`
    - `uUsePrimitivePoints`
    - `uBackgroundColor`
    - `uViewport`
    - 再加矩阵与裁切面相关 uniforms

### 2. 顶点阶段负责把点展开成屏幕对齐 quad

运行时抓到的顶点 shader 关键逻辑如下。

#### 点半径

基础点主路径里：

- `vPointRadius = uDevicePixelRatio * 0.5 * aPrimitiveSize`

这里点尺寸先乘 DPR，再转半径。

#### 点字形参数

- `vPointFont = aPrimitiveStyle.xyz`

也就是说，点字形不是写死在 shader 里的，而是由每个点实例携带。

#### quad 外扩半径

- `pointRadius = vPointRadius + 0.5 * uPointFilterWidth * SQRT2`

这一步非常关键，它不是视觉层面的“多画大一点”，而是为了给片元 AA 留足 coverage 空间。

#### quad 四角

`aPointData` 表示 corner index：

- `1 = 右下`
- `2 = 右上`
- `3 = 左上`
- `4 = 左下`

shader 用它生成四个方向的 `vOffset`，再把 `gl_Position.xy` 推开。

#### 屏幕空间展开

最终位置偏移：

- `gl_Position.xy += (2.0 * gl_Position.w) * (vOffset / uViewport.zw)`

这说明展开发生在 clip-space 中，但量纲由 viewport 控制，最终表现为屏幕对齐的点 quad。

### 3. 片元阶段通过 procedural point-font 生成点形状

基础点片元主入口是：

- `getPointColor(vColor, uBackgroundColor)`

内部核心逻辑如下。

#### 偏移来源

基础 quad 路径用 `vOffset`。

primitive fallback 路径用：

- `(gl_PointCoord - vec2(0.5)) * 2.0 * vPointRadius`

#### point font 三个参数的含义

- `vPointFont.x`
    - 径向分段数
- `vPointFont.y`
    - 角向分段数
- `vPointFont.z`
    - ring 粗细/填充百分比，范围按 0-100 解释

#### 径向逻辑

运行时已确认它会计算：

- `radialStep`
- `closestIndex`
- `closestBoundary`
- `flip`
- `fontAdjustment`
- `radialValue`
- `radialOpacity`
- `radialColorMix`

其中抗锯齿由：

- `smoothstep(-uPointFilterWidth, uPointFilterWidth, ...)`

驱动。

#### 角向逻辑

运行时已确认它会计算：

- `closestAngle`
- 垂线方向
- `perpendicularDistance`

再通过：

- `smoothstep(-uPointFilterWidth, uPointFilterWidth, ...)`

得到角向覆盖。

#### 最外圈边缘

外圈 AA 为：

- `smoothstep(-uPointFilterWidth, 0.0, vPointRadius - distance)`

这说明点的最外边缘是单独一层 perimeter fade，不依赖 ring 逻辑顺带完成。

#### 最终输出

最后输出是：

- `mixedColor = mix(bgColor, pointColor, colorScale)`
- `mixedColor.a *= clamp(opacityScale, 0.0, 1.0)`

这就是为什么 Onshape 的点看起来不是简单的“实色贴上去”。

### 4. point-font 参数与点类别的关系

当前已经有足够证据支持以下映射：

- `point(1, 0, 50)`
    - 普通草图点
- `point(2, 0, 50)`
    - 草图用户点，表现为更明显的空心 ring
- `point(2, 0, 30)`
    - spline handle 一类更细的 ring

这不是纯猜测，而是和：

- bundle 常量
- 本地 point-font 数学
- 运行时 shader 参数语义

三者能够对上。

## Onshape 的点高亮是如何实现的

### 1. 点高亮是独立路径

运行时已经抓到一条单独的点高亮 program。

它不是基础点 shader 上改几个 uniform，而是另一套 draw/program。

### 2. 点高亮同样是 quad billboard

点高亮 draw 同样是：

- `drawElements(mode = 4, count = 6)`

也就是说，基础点和点高亮都不是通用后处理，而是显式重绘点几何。

### 3. 点高亮的尺寸规则独立

高亮顶点 shader 中，点尺寸来自：

- `max(baseSize * uHighlightPointSizeScale, uHighlightPointSizeMin)`

这说明：

- 高亮并不是固定加几像素
- 它有缩放因子
- 同时有最小尺寸下限

### 4. 点高亮的筛选规则独立

高亮路径输入包含：

- `aHighlightId`
- `uActiveHighlightIndex`

shader 会先判断当前点是否属于本次高亮，再决定是否输出，非目标点会被送出可裁掉的位置。

因此高亮不是“整批点统一变色”，而是按点级别筛选后重绘。

### 5. 点高亮的片元逻辑不是 point-font

当前已抓到的高亮片元 shader逻辑更简单：

- 用 `vOffset` 或 `gl_PointCoord`
- 计算 `radius = length(offset)`
- 中心与边缘做一层 alpha 混合
- 最外圈再 fade 掉

这说明：

- 高亮 overlay 不是把基础 point-font 重新跑一遍
- 它更像专用的高亮覆盖层

这也解释了为什么本地的“halo”虽然方向上接近“外层覆盖”，但仍然和 Onshape 不一样：

- Onshape 是点专用高亮 pass
- 不是通用立即模式点 halo
- 也不是单纯画一个更大的同心圆就结束

## primitive fallback 是什么

Onshape 还保留了一条 primitive-point fallback。

当：

- `uUsePrimitivePoints == 1.0`

时，顶点阶段会走：

- `gl_PointSize = uDevicePixelRatio * aPrimitiveSize`

并设置：

- `vPointFont = vec3(1.0, 0.0, 50.0)`

也就是退化成“实心圆”语义。

这说明 Onshape 并没有完全禁用 `gl.POINTS`，但对于草图点主路径，运行时抓到的仍然是 quad billboard 方案。

## 草图编辑态的补充验证

这部分只回答一个问题：

- 进入草图编辑态之后，Onshape 是否换了一套和默认视图完全不同的“点系统”

当前补到的证据说明，不是。

### 1. 当前目标页面里的草图进入链已经跑通

在目标页面里，已经确认下面这条操作链可稳定重现：

1. 左侧特征树双击 `草图 1`
2. 弹出草图配置框
3. 点击右上角确认按钮 `.ns-dialog-button-ok`
4. 草图配置框关闭，页面进入草图编辑态

也就是说，本文后面提到的“草图编辑态”不是猜测，而是在实际接管该页面后反复进入过的状态。

### 2. 进入草图编辑态后，bundle 里仍然是同一个点组件体系

在 Onshape bundle 中，和草图激活直接相关的代码路径包括：

- `displaySketchAsActive(e, t)`
- `displaySketchAsInactive(e)`
- `hasActiveSketch()`

其中 `displaySketchAsActive` 会同时驱动：

- `this.sketchComponent.displaySketchAsActive(...)`
- `this.dimensionComponent.displaySketchAsActive(...)`
- `this.imageComponent.onSketchActivated(...)`

更关键的是，Part Studio 的草图编辑实例化路径中，点对象并不是单独走一套“草图专用 2D DOM 控件”，而是继续由：

- `this.pointBodyComponent.instantiateForPartStudio(e)`

接管。

同一个 bundle 里还明确存在：

- `showPointBodies(e)`
- `hidePointBodies(e)`

并且它们都直接落到：

- `this.pointBodyComponent.hideShowFeature(...)`

这说明草图点在编辑态下仍然属于渲染管线里的 point body / point primitive 体系，而不是进入草图后就换成另一种完全无关的实现。

### 3. 这对点 shader 分析意味着什么

这条补充验证的意义不是“草图编辑态一定 100% 逐指令复用默认视图里的每一个 draw call”，而是把判断边界收窄到更明确的结论：

1. 草图编辑态没有把点渲染切换成一套脱离 WebGL 点 primitive 的新系统
2. 草图编辑态下的点仍然挂在同一个点组件/点 primitive 体系上
3. 因此，前面已经抓到的基础点路径和点高亮路径，不是只对默认视图有效，而是对草图点实现具有直接参考价值

更保守但更准确的表述是：

- 在草图编辑态中，点仍然沿用同一套点渲染架构；当前已经抓到的 `point-font 基础点 + 独立 highlight point pass` 不是偶然旁路，而是 Onshape 点系统的主实现思路

## 当前关于草图点的最终判断

如果把问题继续收缩到“草图点要怎样才能做得和 Onshape 一样”，当前已经可以确定：

1. 不能把草图点理解成普通圆点
2. 不能把草图点高亮理解成通用 halo
3. 不能只调点大小、线宽和颜色
4. 必须对齐 Onshape 的点组件语义、基础点 shader、独立点高亮 pass，以及点类别到 point-font 参数的映射

## 当前已经确认的问题定位

如果只聚焦草图点，本地与 Onshape 的真实差距可以收敛成下面几条：

1. 缺少独立 `pointFilterWidth`
2. quad 外扩半径没有严格按 Onshape 公式走
3. 点最终输出混色逻辑没有严格对齐
4. 点语义分类不够细
5. 点高亮没有走独立点 pass
6. 点高亮尺寸/透明度/筛选规则没有和 Onshape 同构

## 对后续实现的直接含义

在不改代码的前提下，当前已经可以明确后续真正要对齐的不是“换个圆点样式”，而是下面这些底层机制：

1. 基础点与点高亮分成两条路径
2. 基础点使用独立 point shader uniform
3. 基础点使用 point-font 参数化字形
4. 基础点 quad 展开半径包含 filter width 预留
5. 高亮点使用独立高亮尺寸、透明度、颜色和筛选机制
6. 从草图语义层显式传递点类别与点状态

## 仍待补齐的最后验证

当前已经足够说明 Onshape 的“点”总体实现结构，但还剩一个需要补齐的边界：

- 草图编辑态下的 `sketch point` 与当前默认视图下捕获到的点高亮 pass，是否完全同一套高亮 program

这不会推翻本文结论，只会把“点高亮独立 pass”从高可信提升到草图点场景下的直接实锤。

## 最终结论

当前最重要的判断已经成立：

- Onshape 草图点的基础渲染，是 procedural point-font
- Onshape 点高亮，不是通用 halo，而是独立的点高亮 pass

所以本地后续如果要真正做成“和 Onshape 一样”，不能只在现有点 shader 上微调参数，也不能继续把 halo 当成等价实现。

必须把：

- 点语义
- 点专属 AA
- 点 quad 展开
- 点最终混色
- 点高亮独立 pass

这几个底层机制一起对齐，结果才会接近 Onshape。
