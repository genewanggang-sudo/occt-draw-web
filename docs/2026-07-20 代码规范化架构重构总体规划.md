# 代码规范化架构重构总体规划

更新日期：2026-07-20

## 1. 定位

本文件是 `occt-draw-web` 当前唯一有效的工程规划文档。它定义一次以行为保持为前提的大规模代码规范化重构：将已有实现整理为职责单一、命名稳定、易于定位的架构，同时不改变产品功能、渲染结果、交互时序、数据格式和 package 边界。

本次工作不是功能开发，不借机修复交互问题、优化性能、替换渲染算法或改变 UI。发现的问题应记录在批次审查中，另行冻结范围后处理。

用户已明确授权 math 批次对两个根入口自由函数进行直接迁移：sampleCurveSegments2 迁移为 CurveTessellator2.tessellate，createRegularPolygonPoints 迁移为 RegularPolygon2.create。除此以外，既有公开契约默认保持兼容；如需扩大公开 API 的破坏范围，必须先重新冻结并获得明确授权。

## 2. 已确认的产品基线

### 2.1 工作台与文档

- React 工作台包含特征树、属性面板、命令工具栏、草图编辑面板，以及打开、保存、撤销和重做。
- 默认 CAD 文档包含 Part Studio、原点和 XY/YZ/ZX 基准面。
- 文档通过 JSON 编解码打开和保存；序列化格式、字段、ID 和版本语义属于兼容契约。

### 2.2 草图编辑

- 可以选择基准面进入草图，确认时合并编辑 scope，取消时回滚；也可以从特征树再次进入草图编辑。
- 已接通临时 Draft 预览和正式 document request 提交的工具包括：点、直线、中点线、样条、拐角矩形、中心矩形、对齐矩形、圆、三点圆、内切/外接正多边形、三点圆弧、相切圆弧、圆心圆弧、椭圆、椭圆弧和圆锥曲线。
- 支持对象与草图实体拾取、悬停预选、活动草图顶点拖拽、删除草图实体、撤销和重做。
- `extrude` 目前只有命令定义和 UI 入口：`hasSketchProfile` 仍恒为 `false`，没有可执行的 ExtrudeCommand。约束、尺寸和 profile 也是数据占位，不应在本次重构中扩展。

### 2.3 渲染与视口

- CAD 文档、草图和 Draft 会先投影为 `CanvasScene`，再转换为 `RenderGraph`。
- WebGL2 当前生产渲染顺序固定为 `ColorPass -> HighlightPass -> OverlayPass`。`WebGLRenderer` 负责场景缓存路径，`WebGLImmediateRenderer` 仍用于高亮与叠加即时绘制，两者不可合并或互换。
- 支持基准面、标签、活动草图平面、草图边/曲线/顶点/自由点、临时预览、选择与预选高亮。
- 支持右键旋转、中键平移、滚轮缩放、适配视图、标准视图、ViewCube 面/角/箭头操作和导航深度采样。

## 3. 不可变约束

1. 不新增、删除、合并或拆分 workspace package。任何 package 层级调整都必须先获得用户明确确认。
2. 未经用户明确同意，不修改 `AGENTS.md`。
3. 不新增测试文件，也不为本次规范化重构改写现有测试文件。
4. 不改变根 `package.json` 的用户已有改动，也不夹带依赖升级、构建配置调整或格式化全仓库。
5. `apps/web` 只能依赖 `@occt-draw/editor` 与 `@occt-draw/ui`；其他依赖白名单继续由 `dependency-cruiser.cjs` 约束。
6. package 根 `src/index.ts` 是唯一公开入口。已有导出符号、构造参数、返回值、事件顺序和持久化格式必须保持兼容；第 1 节已列出的两个 math 自由函数迁移是已批准的例外。
7. 规范化阶段不改变 render pass 顺序、shader source、uniform/attribute 协议、GPU 状态、对象 ID、primitive metadata、dirty flag/cache key 语义，或 `EditorViewport.sync()` 的图重建与渲染时机。
8. 任何 Onshape 或其他外部资料的下载、截图、脚本和分析产物只放入 Git 忽略的 `tmp/`；每个分析目录应有可检索的 `INDEX.md`，不得再次写入 `docs/` 或提交。

## 4. 当前分层与关键调用链

```txt
apps/web -> editor, ui
editor -> cad-canvas, cad-model, canvas, platform, sketch, snapping, core, math
cad-canvas -> cad-model, sketch, core, canvas, math
platform -> canvas, snapping, core, math
canvas -> webgl-engine, math
cad-model -> sketch, core, math
sketch / snapping -> core, math
core / webgl-engine -> math
math / ui -> no workspace dependency
```

编辑和渲染主链必须保持不变：

```txt
React App
  -> Application.initCanvas()
  -> EditorViewport
  -> RenderEngine

EditorState sync
  -> createEditorRenderGraph()
  -> CadCanvasAdapter.createScene()
  -> CanvasScene
  -> CanvasRenderGraphProjector
  -> RenderGraph
  -> ColorPass -> HighlightPass -> OverlayPass
```

输入、选择和相机主链必须保持不变：

```txt
DOM pointer / wheel / key
  -> ViewportInput
  -> ViewportInteractor
  -> ViewCubeController
  -> CommandManager
  -> EditorDefaultController
  -> CameraNavigationController

selection pick
  -> EditorViewport.pickSelectionTarget()
  -> PickService
  -> CanvasPickService
  -> RenderObjectPicker
```

当前 `legacy/*` 是旧 RenderScene/RenderNode 与新 RenderGraph/RenderObject 的内部兼容适配，不是当前应用渲染主路径。规范化过程中只隔离、审计和保留其兼容性；是否删除必须作为最后一个单独批次确认。

## 5. 一文件一类规范

“一文件一类”在本项目中的可执行定义如下：

1. 每个可实例化的领域类、控制器、命令、渲染对象、pass、adapter、store 或 React 组件只有一个主文件，文件名与主导出名一致，例如 `Sketch.ts`、`AddCircleRequest.ts`、`ViewCubeController.ts`。
2. 一个实现文件最多承载一个同级主运行时抽象。描述该抽象的输入、输出、私有 helper type 和常量可以就近保留；跨文件或跨 package 的稳定契约独立为主题明确的 `*Types.ts` 文件。
3. 数学算法、构造、映射、校验、状态转换和 helper 均不得作为模块级自由函数存在。凡是能形成职责或概念的实现，必须归属到命名清晰的类的实例方法或静态方法；只保留类型、接口、常量和确实不具备运行时概念的语言级定义。私有且只服务于一个类的细节可作为该类的私有方法保留，不为形式制造空洞的包装类。
4. `index.ts` 只负责公开 re-export，不承载运行时业务、类实现或跨层编排。
5. 每次拆分后，调用方仍通过原 package 根入口或原有内部门面导入。允许新增内部目录和兼容 re-export，禁止跨 package 深导入来绕过边界。
6. 大类可拆出协作对象，但保留原类作为门面，直到所有调用点完成稳定迁移；除已在计划中获得用户明确授权的 API 迁移外，不将纯重构和 API 重设计放在同一批次。
7. 类的依赖必须通过构造参数或明确的上下文对象注入；不引入隐藏单例、循环 import 或运行时动态装配来规避拆分难度。

## 8. 每批执行协议

1. 冻结范围：列出要移动、创建、删除和保留门面的每个文件，写明不触碰的邻近模块。
2. 冻结契约：记录 package 根导出、运行时调用顺序、序列化字段、对象 ID 和关键输入/输出。
3. 记录视觉基线：启动现有 Web 应用，将截图、操作记录和外部资料放在 `tmp/` 对应批次目录，并建立 `INDEX.md`。
4. 只做结构提取、移动和 re-export；发现行为修复、性能优化、样式调整或包边界需求时停止并单独规划。
5. 执行静态检查：`pnpm lint`、`pnpm -r typecheck`、`pnpm depcruise` 和 `pnpm --filter @occt-draw/web build`。不新增或修改测试文件。
6. 以浏览器视觉和交互验收为准，完成本批相关路径后进行代码审查；所有发现的问题必须在本批修复后才可提交。
7. 暂存本批文件，确认 `git diff --cached` 不含用户无关改动，再提交一个语义明确的 commit。

## 10. 完成标准

本次规范化重构完成时，应同时满足：

- 每个运行时类和 React 组件都有唯一、可预测、以名称命名的主文件。
- 不再存在承载多个同级业务类的大型聚合文件；运行时代码只存在于职责明确的类中，类型、接口、常量和 re-export 文件保持单一概念边界。
- 所有 package 的根导出、依赖方向、document 文件格式、交互顺序和渲染输出保持兼容，已授权的两个 math API 迁移除外。
- 每个批次都有冻结范围、浏览器验收记录、审查结果和独立 commit。
- 不新增测试文件，不新增 package，不将外部分析产物提交到仓库。

## 11. @occt-draw/math 全量架构冻结

### 11.1 范围与目标

本节冻结第 1 批的整体设计边界，范围覆盖 packages/math/src 的 value、linear、coordinate、geometry-2d、geometry-3d 与 query。目标不是机械地把每个函数移入任意 class，而是让每个运行时概念都有唯一、可发现的所有者：

- 领域对象保存自身不变量与核心行为；
- 值对象表示不可变数值、参数、角扫掠、输入规格或计算结果；
- 算法、构造、拟合、离散化与跨对象查询由命名计算器、构建器、工厂或协调器承担；
- 同一概念的私有细节留在其所属类中，绝不以模块级 helper 存在；
- package 不增删、不调整依赖层级；只允许在既有 math 包内部增加一文件一类的子目录。

当前所有 39 个模块级函数都必须在本批的目标类中有明确归属。现有草稿中仅按文件移动的 CurveParameter、ParameterDomain、EllipticalArc2 与 Nurbs2 不是完成形态，必须纳入以下整体设计后再继续实现。

### 11.2 依赖方向

    不可变 value
        -> linear
        -> coordinate
        -> 2D/3D 基础几何实体
        -> 曲线定义、构造、离散化与样条协作类
        -> 查询计算器
        -> 不可变结果对象

GeometryResult 属于 value 基础层，因此可被所有后续层返回。基础几何实体不得依赖 query、拟合或 UI；查询计算器只依赖稳定的几何实体与 value/linear；根 index.ts 只做 re-export，不能承载运行时逻辑。不存在反向导入、运行时服务定位或隐藏默认实例。

### 11.3 领域类与职责

| ----------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |

### 11.6 数据与生命周期边界

- 值对象、几何实体、样条定义和结果对象均不可变；构造时复制可变输入数组和向量，输出不与下一次计算共享可变状态。

- FitSpline2Interpolator 的一次调用只创建本次规格、参数集、约束系统和求解结果；这些中间对象不泄漏到后续调用。
- 兼容门面无实例生命周期、无缓存、无全局服务定位。DEFAULT_TOLERANCE 是公开的不可变规范值，不属于隐藏单例。

- BSpline2、Nurbs2 的构造参数、controlPoints、degree、knots、domain、isValid、pointAt、tangentAt 和 FitSpline2 的全部公开字段及 fromFitPoints 签名保持不变；

- BSplineBasisEvaluator 是唯一拥有 Cox-de Boor 值、导数和二阶导数递归的类。BSpline2 与 NURBS 只消费 basisValues，FitSpline2ConstraintSystemBuilder 只消费 rowAt；

- FitSpline2ConstraintSystem 将二维右端值映射为 LinearEquationSystem；GaussianEliminationSolver 返回 GeometryResult<readonly number[]>，保持奇异系统最终映射为 FitSpline2 的 degenerate；
- FitSpline2Interpolator 以显式 Tolerance 生命周期按 验证 -> 参数化 -> 节点 -> 基函数定义 -> 约束 -> 求解 -> BSpline2 -> FitSpline2Interpolation 协调；FitSpline2.fromFitPoints 只委托该协调器并将成功的中间值包装为 FitSpline2，失败状态原样映射，不能再包含任何算法 helper；
- FitSpline2Interpolation 是不可变中间值对象，用于避免 FitSpline2 与 FitSpline2Interpolator 的循环 import；它保存构造 FitSpline2 所需的完整、已验证状态。

数值与状态硬约束：

- BSplineBasisDefinition 只有在 degree 为整数且不小于 1、controlPointCount 大于 degree、节点数量等于 controlPointCount + degree + 1、节点有限且非递减时有效；参数域严格取 knots[degree] 到 knots[controlPointCount]，且长度必须大于零；
- LinearEquationSystem 必须是严格 N×N 系数矩阵与长度为 N 的常数向量。FitSpline2ConstraintSystem 的 N 必须同时等于 controlPointCount 和 fitPoints.length + 2，x/y 右端值也必须均为 N；
- 求解结果 x/y 只有在长度均为 N 且全部有限时才可配对为 Vec2；严禁使用 y[index] 的默认值、填零或任何补值路径，任一维度、有限性或有效性不符都返回 degenerate；
- FitSpline2Specification 对任何输入 degree 都继续归一为 3；closed 继续只保存元数据，不改变节点或约束；存在切线时使用一阶导数行与该切线 RHS，不存在切线时使用二阶导数行与零 RHS；
- 少于 3 点或任何非有限点/切线返回 empty；无可用点跨度、参数化失败、奇异方程、无效基函数定义或无效生成曲线返回 degenerate；
- FitSpline2ConstraintSystemBuilder 只能从 BSplineBasisDefinition 及其 BSplineBasisEvaluator 取得 rowAt，绝不构造带占位 Vec2 的 BSpline2/BSplineDefinition2 来间接求基函数。

数据与生命周期：定义、节点、参数集、约束系统和求解结果均为一次拟合调用内的不可变值对象；验证器、参数化器、构建器、求值器和求解器通过显式构造或参数创建，不缓存隐藏默认实例。所有新算法都必须是所属类的实例方法或静态方法；bspline2.ts、nurbs2.ts 与 fitSpline2.ts 完成后不得再有模块级 function。

领域概念、职责、接口与依赖方向：Matrix3 和 Matrix4 分别是二维齐次矩阵、三维齐次矩阵的不可变值对象；唯一拥有自身的 Float32Array 内部表示、矩阵乘法和点/向量变换。Bezier2、BSpline2、FitSpline2、Polygon2 与 Polyline2 分别拥有其曲线/多边形定义的 Vec2 序列快照；Nurbs2 在 BSpline2 基础上唯一拥有权重序列快照。Coord3 是正交三维坐标框架值对象，唯一拥有原点和三根轴的私有 Vec3 快照；OBB3 是由已封装 Coord3 框架和半尺寸向量定义的不可变有向包围盒值对象，安全共享 Coord3，并唯一拥有 halfSize 快照，不新增几何查询职责。稳定接口保持为 `new Matrix3(elements?)`、`new Matrix4(elements?)`、`elements`、`toFloat32Array()`、所有既有 factory/计算方法，Bezier2/BSpline2 的 `controlPoints`，BSpline2 的 `knots`，Nurbs2 的 `weights`，FitSpline2 的 `fitParameters`/`fitPoints`，Polygon2/Polyline2 的 `points`，Coord3 的 `origin`/`xAxis`/`yAxis`/`zAxis`，以及 `new OBB3(frame, halfSize)`、`frame`、`halfSize`；这些属性的静态类型和读取方式均不变，集合/向量属性每次读取返回独立数组或独立 Vec2/Vec3。OBB3.frame 保持既有 Coord3 实例身份，但该 Coord3 已无可经公开 API 改写的状态，因而不会泄露 OBB3 定义。不得制造通用 CollectionSnapshot/MatrixBuffer 空壳类：序列快照的所有权、元素复制规则和寿命均由具体几何值对象的领域不变量决定，通用包装会掩盖该职责并引入无稳定业务接口。依赖方向保持为 `value -> Vec2/Vec3 -> Matrix3/Matrix4、2D 几何、Coord3 -> OBB3 -> barrels`；不得引入 query、geometry-2d 反向依赖或跨 package 依赖。

数据与生命周期边界：矩阵构造仍按既有 Float32Array 转换规则复制输入；私有元素数组在实例存续期间绝不泄露，`elements` 与 `toFloat32Array()` 每次读取均返回新 Float32Array，调用者修改返回值不得影响该矩阵或后续计算。每个 2D 几何类在构造/插值完成时建立自己的私有序列；Vec2 数组 getter 必须同时复制数组与每个 Vec2，number 数组 getter 必须复制数组，曲线、多边形、NURBS 的内部计算一律只读私有快照。BSpline2 仅为 NURBS 继承关系提供受保护的控制点数量/按索引读取入口，不得把数组暴露给子类；Nurbs2 权重访问只归 Nurbs2。Coord3 在构造期仍按原有规则归一化/正交化一次，之后只读取私有轴快照，四个公开 getter 都返回 Vec3 副本；OBB3 因此直接保存并返回该安全 Coord3 引用，绝不以 `new Coord3(...)` 重建 frame，从而保持既有 frame 的精确数值和身份。OBB3 的 halfSize getter 返回独立 Vec3，其公开静态类型继续为 Vector3。不得新增缓存、模块级 helper、默认服务实例或新的运行时导出；Matrix3/Matrix4 现有 `get` 与 `identityElements` 仍分别归属自身私有静态方法，所有序列快照/getter/helper 均只归其宿主类。不得借本批增加长度/有限性校验、改变矩阵列主序、浮点精度、乘法顺序、错误行为、坐标框架数值、曲线/多边形数值、NURBS 权重语义或 OBB3 合法性语义。

本批受保护且不修改的邻居为 `vec2.ts`、`vec3.ts`、`linear/index.ts`、`geometry-2d/index.ts`、`geometry-3d/index.ts`、math 根入口、所有 query、spline 定义/求值器、其余 curve 类、所有跨 package 调用方、测试、配置及 package 分层。实施顺序为：先替换两个矩阵的内部存储访问，再按 Bezier2/BSpline2/Nurbs2/FitSpline2/Polygon2/Polyline2 的既有继承与组合方向收回集合快照，随后封装 Coord3 向量快照，最后让 OBB3 共享安全 frame 并收回 halfSize；随后全量检索确认 math 无模块级 function、隐藏 defaultXxx 或可变内部数组泄露。静态验收执行 math test、全 workspace typecheck、lint、depcruise、格式检查和 Web build；浏览器以干净页面验收 WebGL2、ViewCube 和草图基本选择路径。代码审查必须检查输入、getter 输出与内部计算的双向隔离，BSpline2/Nurbs2 继承接口、Coord3/OBB3 数值与身份兼容和无新依赖循环；发现问题须在本批提交前修复。

完成记录：独立审查发现 OBB3 初版通过 `new Coord3(...)` 复制 frame 会重新归一化并引入微小数值漂移；已将 Coord3 先收口为私有 Vec3 快照与防御性 getter，使 OBB3 可安全保持原有 frame 身份与分量精确值。复审确认 10,000 组随机 frame 均无重构前后分量漂移，输入/输出向量、数组、typed-array 与 halfSize 的修改均不会影响内部计算；BSpline2/Nurbs2 受保护访问不暴露控制点数组，math 无模块级 function 或 `defaultXxx`。`pnpm --filter @occt-draw/math test`、全 workspace `typecheck`、`lint`、`depcruise`、格式检查与 Web build 均通过。浏览器在最终干净页面确认 WebGL2 ready 且控制台无 error，并成功选择前基准面进入草图。
