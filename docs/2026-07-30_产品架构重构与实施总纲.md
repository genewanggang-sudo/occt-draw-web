# 产品架构重构与实施总纲

更新日期：2026-07-30
状态：当前唯一有效的工程总纲

## 1. 产品目标

`occt-draw-web` 的目标是实现尽可能接近 Onshape 的 CAD 产品。架构重构服务于可持续交付，而不是独立的代码整理活动：每一项结构改动都必须让后续的建模、草图、特征、交互和渲染能力更容易安全地实现。

产品行为必须保持稳定，包括文档 JSON、对象 ID、撤销/重做顺序、输入时序、拾取语义、GPU 状态、Pass 顺序和可见渲染结果。未经单独冻结，不借重构修改算法、性能、样式或产品功能。

## 2. 单一真源与当前基线

本文件是 `docs/` 下唯一的执行总纲。历史规划中的详细批次记录由 Git 提交历史保留，不再与当前策略并列为执行依据。

本轮总纲以同步后的 `main` 提交 `1337f12` 为代码基线。其中 `c2f47f7` 至 `6adb92a` 已导入一组 `@occt-draw/math` 重构提交；它们是待验收的现状，不因已合并而自动视为符合本总纲。下一批必须先完成该基线的集成审查，再决定是否存在需要收口的 math 缺口。

## 3. 不可变架构边界

1. 不新增、删除、合并或拆分 workspace package；不移动模块到其他 package，不改变 package 职责或依赖方向。
2. package 根 `src/index.ts` 是公开入口；跨 package 调用继续使用根入口，不以深层导入、循环依赖或隐藏全局状态规避设计问题。
3. 不保留 compatibility facade、wrapper、alias、shim、deprecated export 或双 API。需要调整入口时，在同一批直接迁移所有调用方并删除旧入口。
4. 每个运行时主类、控制器、命令、渲染对象、Pass、adapter、store 或 React 组件有唯一职责明确的主文件。与类相关的辅助逻辑归属为该类的 private、protected 或 private static 方法；不新增 `utils`、`helpers`、`common` 等收容文件。
5. React 函数组件、Hooks 和职责明确的数学纯计算 API 可以保持函数形式；其余运行时行为必须有明确 owner。`index.ts` 只负责 re-export。
6. 不新增或修改测试文件；每批使用静态检查和浏览器视觉、交互验收。未经明确同意，不修改 `AGENTS.md`、依赖、构建配置或文档格式。

## 4. 调研与验收原则

Onshape 固定参考链接：

https://cad.onshape.com/documents/cb24420a26a5ed84801750a9/w/6afad649721589e7fdfade2a/e/86ba8a42171d7bde0922e59d

若链接重定向到登录页，停止该调研步骤并通知用户登录。Onshape、Autodesk 或其他外部资料的下载、截图、脚本、分析记录和索引只放入 Git 忽略的 `tmp/`，每个分析目录必须有 `INDEX.md`，不得提交。

涉及运行时代码时，静态检查之外必须在浏览器中验收受影响路径；至少覆盖 WebGL2 就绪、选择与预选、草图进入和退出、受影响工具的预览与提交、相机导航、打开和保存。不得用新增测试文件代替视觉验收。

## 5. 实施路线

### 5.1 立即执行：已同步 math 基线的集成审查

范围仅限 `c2f47f7` 至 `6adb92a` 的 `@occt-draw/math` 改动及其直接 workspace 调用方。审查以下事项：

- 每个运行时概念是否有唯一 owner，是否残留模块级 helper、默认实例或兼容层；
- 根导出、调用方迁移、依赖方向和 package 边界是否符合本总纲；
- 已批准迁移的 `sampleCurveSegments2` 与 `createRegularPolygonPoints` 是否已让所有调用方直达真实 owner，且旧入口没有作为 alias 或兼容 API 保留；
- 数值、结果载荷、不可变快照和几何查询的既有行为是否保持；
- 静态检查与浏览器基础 CAD 路径是否通过。

该审查只产出验收结论和明确缺口。若发现问题，先冻结一个最小、完整的收口批次；不得在审查中顺手扩大重构范围。

### 5.2 后续架构收口顺序

在 math 缺口关闭后，按以下依赖顺序推进，每次仅选择一个最小完整批次：

`math -> core -> sketch -> cad-model -> webgl-engine -> canvas/cad-canvas -> platform/snapping -> editor -> ui/apps -> legacy 审计`

`legacy` 只在确认无消费者后单独处理。每个阶段先全量审计对应目录、barrel 和调用方，再冻结实际批次；不得以少数热点文件代替整个阶段范围。

### 5.3 产品能力推进

架构基础稳定后，产品功能按完整 CAD 工作流交付：文档与 Part Studio、草图实体与约束、profile、特征请求与可执行 Extrude、持久化与撤销/重做、拾取与交互反馈。每项功能单独冻结，复用经调研验证的 Onshape 交互、Shader 或 Pass 设计，不与无关架构收口混在同一批。

## 6. 每批强制门禁

1. 冻结范围：说明目标、非目标、文件清单、领域 owner、删除的旧入口、调用方迁移和受保护契约。
2. 自审计划：检查是否跨 package、是否引入兼容层、是否遗漏调用方、是否把功能变化混入结构批次；发现问题先修订计划。
3. 实施一个最小且功能完整的改动；遇到未计划的行为、数据格式、依赖或范围变化立即停止并请求确认。
4. 自审改动并修复发现的问题，运行适用静态检查，完成浏览器验收，将调研和验收记录放入 `tmp/`。
5. 报告改动与验收结果后停止，等待用户审查。未经用户明确指令，不进入下一批、不提交也不推送。

## 7. 完成标准

- `docs/` 保持一份当前有效的工程总纲，不存在相互冲突的实施说明。
- 每个运行时行为均有清晰 owner，且不存在兼容层、双入口、无归属 helper 或违反依赖方向的实现。
- 所有实际批次都保留 package 边界、数据和交互契约，通过静态检查和浏览器验收，并在用户审查后进入下一步。
- CAD 产品能力以完整可用工作流递增，而不是以孤立组件或未验证的重构记录递增。
