# 草图编辑环境与命令架构重构记录

日期：2026-06-02

## 背景

近期草图交互能力已经推进到线、矩形、圆、三点圆、椭圆、草图显示选项等功能，但当前实现逐渐暴露出架构问题：每个草图命令都在重复处理草图上下文、投影、临时状态、draft 预览、取消策略、document request 提交等逻辑。

这说明继续给单个 command 增加 helper 只是临时方案。更合理的方向是补齐编辑器应用上下文、环境管理和草图编辑环境，让公共能力有明确归属。

## 当前项目现状

当前项目还没有完整的 `Application + EnvironmentManager + Environment` 模型。

现有结构大致是：

```txt
apps/web/src/app/App.tsx
  React 组件入口，不是编辑器 Application

EditorViewportRuntime
  管 canvas、renderer、input、ViewportInteractionController

ViewportInteractionController
  管 CommandManager、输入分发、导航兜底

EditorState.activeSketchSession
  记录草图编辑状态，但不是一个真正的 SketchEnvironment

CommandManager
  当前已经是全局命令管理器
```

当前问题是：`activeSketchSession` 只是状态字段，缺少承载草图编辑规则和服务的对象。因此 `SketchLineCommand`、`SketchCircleCommand` 等命令只能自己读取 state、自己维护临时状态、自己清理 draft、自己构造 document request，导致命令越来越胖。

## 目标模型

后续应当把编辑器架构调整为：

```txt
EditorApplication / EditorRuntimeContext
  -> commandManager
  -> environmentManager
  -> documentSession
  -> selection
  -> navigation
  -> picking/rendering services

EnvironmentManager
  -> DefaultEnvironment
  -> SketchEnvironment

CommandManager
  -> 统一管理所有命令

CadCommand
  -> 所有命令基类

SketchCommand
  -> 草图命令基类
  -> 通过 app/environment 获取当前 SketchEnvironment

SketchDrawLineCommand
SketchDrawCircleCommand
SketchDrawRectangleCommand
  -> 草图环境内的具体绘制命令
```

关键原则：

1. `CommandManager` 仍然是唯一命令入口。
2. 进入草图后，不新建一套独立 command manager。
3. `SketchEnvironment` 是草图子编辑器上下文。
4. 草图内的画线、画圆、矩形仍然是 command，但应继承 `SketchCommand`。
5. `SketchCommand` 不直接到处读写散落状态，而是通过当前 `SketchEnvironment` 获取草图上下文和公共能力。

## 职责边界

### EditorApplication / EditorRuntimeContext

负责承载编辑器运行时服务：

- 当前 `EditorState` 的读取和更新。
- `CommandManager`。
- `EnvironmentManager`。
- document session / history。
- selection。
- navigation。
- picking/rendering 相关服务。

它不是 React 组件，而是编辑器应用层上下文。

### EnvironmentManager

负责当前编辑环境：

- 默认环境。
- 草图环境。
- 后续可能的装配环境、特征编辑环境等。

它的职责是管理“当前处于什么编辑上下文”，不是管理命令表。

### DefaultEnvironment

默认进入应用时的环境。

负责：

- 普通选择。
- 普通实体编辑入口。
- 默认导航/拾取策略。
- 非草图状态下的快捷键处理。

### SketchEnvironment

进入草图后激活。

负责：

- 当前 `sketchFeatureId`。
- 当前草图平面和坐标系。
- 当前草图数据查询。
- 草图选择过滤。
- 草图内 draft / preview 生命周期。
- 草图确认和取消。
- 草图事务边界。
- 草图公共投影、吸附、默认约束策略入口。

`SketchEnvironment` 不应该自己维护一套命令管理器。

### CadCommand

所有命令的基础类型。

负责：

- 统一的命令生命周期接口。
- 输入处理入口。
- 通用 command result 协议。

### SketchCommand

草图命令基类。

负责：

- 检查当前环境是否为 `SketchEnvironment`。
- 提供 `getSketchEnvironment()`、`getSketchContext()` 等草图命令公共入口。
- 统一处理草图命令不在草图环境下执行时的 blocked/message。

它不负责具体画线、画圆、画矩形的业务状态机。

### SketchDrawLineCommand

草图环境内的具体绘制命令。

负责：

- 画线交互流程。
- 组合取点/吸附/拖拽等交互状态。
- 生成线段编辑 request。

不负责：

- 进入/退出草图。
- 保存当前草图上下文。
- 全局 command 注册。
- document history 的底层实现。
- 通用投影/吸附/约束策略的完整实现。

## 外部参考结论

### Onshape

通过 Chrome 调试 Onshape 生产 bundle 得到的确定结构是：

- 有 `currentSketchCommand` 记录当前草图命令。
- 有 `startTool` / `switchTool` / `escapeCurrentSketchCommand` 这类命令入口。
- 有 `activeCreationController` 承载当前草图工具的创建交互。
- 切换草图工具时，会集中 abort 当前 creation controller，再创建新的 controller。

这说明草图工具不是脱离草图的大编辑器，而是草图编辑上下文内的工具/创建控制器。

### Revit

Revit API 中存在明确的 `SketchEditScope`。

Revit 的模型是：

```txt
ExternalCommand
  -> 入口

SketchEditScope
  -> 草图编辑作用域

Transaction
  -> 文档修改事务
```

这支持一个结论：草图应当是编辑作用域，真正修改模型必须进入事务边界，不能让 command 自己长期持有全部编辑上下文。

### yt-sscs

`D:\work\yt-sscs` 中已有类似模型：

```txt
Application
  -> CommandManager
  -> EnvironmentManager
  -> RequestManager
  -> SelectManager

SketchEnvironment
  -> 草图子编辑器

DrawLineSegmentCommand
  -> 草图环境内画线命令

SnapPointState / PickPointState
  -> 可复用交互状态

SketchRequests.AddEdge
  -> 真正修改草图数据

RequestManager / Session
  -> undo / redo / transaction
```

它验证了一个方向：草图环境负责上下文，草图命令负责交互，数据修改下沉为 request/session。

## 后续改造建议

建议按低风险顺序推进：

1. 新增编辑器运行时上下文概念，但先不改变跨包依赖。
2. 新增 `EnvironmentManager` 和 `DefaultEnvironment` 的内部实现草案。
3. 将 `activeSketchSession` 包装为 `SketchEnvironment` 可读取的上下文，而不是立即大规模改 state。
4. 新增 `SketchCommand` 基类。
5. 先选择最简单的 `SketchDrawLineCommand` 做试点。
6. 抽取取点/投影/吸附/draft preview 的交互状态。
7. 将默认约束、吸附约束、合法性判断逐步从具体 command 中移出。
8. 再迁移 circle / rectangle 等命令。

任何涉及跨 package public API、导出项、request 类型或共享 helper 的改动，都需要先做包职责与改动边界确认，再开始编码。
