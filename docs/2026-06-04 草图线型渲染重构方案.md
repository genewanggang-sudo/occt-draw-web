# 草图线型渲染重构方案

创建日期：2026-06-04

最近复核：2026-06-04

状态：实施规格文档。阶段 1 已验收；阶段 2 到阶段 6 已作为当前未提交改动实现并通过本地检查；Onshape 圆心圆弧两阶段截图对照已完成。

## 目标

建立一套清晰的草图线型显示架构，让业务命令只表达“这条线是什么语义”，渲染层统一决定“这条线怎么画”。

本轮目标是线型和线条显示，不是继续新增草图工具。

最终要达到：

- 圆心圆弧预览行为和 Onshape 对齐。
- `solid`、`construction` 等线型语义不散落在命令和 shader 里。
- 草图预览线、模型线、hover、高亮、选中线走同一套线渲染能力。
- editor 命令不包含 dash、线宽、shader uniform、WebGL 常量。

## 非目标

这些内容不要混进本轮线型重构：

- 不实现动态尺寸文本输入。
- 不实现约束求解。
- 不重构草图命令架构。
- 不改变 package 依赖关系。
- 不照抄 Onshape 压缩后的前端源码。

Onshape 在圆心圆弧预览时会显示半径尺寸文本，例如 `R120.99`。本文只处理线和点的预览显示；尺寸文本后续应单独立项。

## 执行规则

后续按本文实施时必须遵守：

- 涉及两个及以上 package/app 的源码改动，编码前先输出“包职责与改动边界确认”。
- 新增、删除或修改 public API、导出项、共享 DTO、跨包类型时，编码前先确认影响范围。
- 不新增 workspace package 依赖。
- 每个阶段完成后运行对应验收；涉及渲染行为的阶段必须做浏览器截图验证。
- 能从 Onshape 浏览器行为或本地保存的 Onshape bundle 中确认的交互行为、显示链路和渲染参数职责，优先按 Onshape 对齐。
- Onshape 只作为行为、显示链路和职责分层基准，不作为源码复制来源。
- Onshape bundle 无法确认的内部实现细节，按本项目现有 package 职责设计，不反推或臆造。

## Onshape 已确认行为

### 浏览器观察

通过 Chrome 接管 Onshape Part Studio 标签，在草图编辑状态下选择“圆心圆弧”工具，观察到两个阶段：

1. 第一次点击确定圆心后，移动鼠标确定半径和起点。
    - 显示完整参考圆。
    - 显示圆心到当前半径点的参考线。
    - 参考圆是 construction 虚线。
    - 半径参考线也是 construction 虚线。
    - 显示圆心点和当前半径点。
    - 显示半径尺寸文本。

2. 第二次点击确定起点后，移动鼠标确定终点方向。
    - 完整参考圆消失。
    - 半径参考线消失。
    - 只显示最终会生成的圆弧预览。
    - 圆弧是 solid 实线。
    - 圆弧预览显示圆心、起点和终点相关点标记。
    - 本次复核截图中半径尺寸文本仍显示，但不属于本文线型重构目标。

### Onshape 当前线渲染实现分析

本地 `docs` 下保存的 Onshape 前端 bundle 只能作为行为和显示链路参考，不能作为可照搬源码。
下面这些结论来自本地 bundle 中可直接检索到的显示链路，不是按截图反推。

#### 1. 草图实体先决定显示语义

`docs/webgl.cb17e4d077a949b1db67.js` 中，草图实体样式会先判断实体类型和草图语义：

- edge / face / vertex / degenerate edge 会走不同 z offset、priority、pick/highlight 策略。
- edge 会判断 `isSketchConstructionEntity()`。
- construction edge 不直接在业务命令里写 dash 数组，而是在显示样式阶段选择 `CONSTRUCTION_LINE_STIPPLE`。
- 非 construction edge 使用 `DEFAULT_LINE_STIPPLE` 或 show-through 对应的默认 stipple。
- 最后通过类似 `COLOR`、`PRIMITIVE_SIZE`、`PRIMITIVE_STYLE` 的属性把颜色、线宽、线型交给后续渲染节点。

这说明 Onshape 的第一层不是 shader，而是“草图实体语义 -> 显示样式属性”。
因此本项目里 editor / command 只应该表达 `solid`、`construction` 这类语义，不能写 WebGL dash 数组。

#### 2. Material 持有线宽和线型参数

`docs/webgl.cb17e4d077a949b1db67.js` 的材质初始化里可以确认：

- 默认 material 有 `lineWidth`，来源是 `DEFAULT_LINE_WIDTH`。
- 默认 material 有 `lineStipple`，来源是 `DEFAULT_LINE_STIPPLE`。
- construction 线型通过 `CONSTRUCTION_LINE_STIPPLE` 进入显示样式。

这说明 line width 和 line stipple 是显示/材质层数据，不是草图命令内部状态。
本项目对应的职责应该落在 `webgl-engine` 的 line render style resolver，而不是分散在各个草图 command 里。

#### 3. Render pass 下发线条 uniform

bundle 中可确认 WebGL pass 会下发这些和线条有关的 uniform：

- `uLineFilterWidth`：线边缘 fall-off 宽度，用于抗锯齿。
- `uBackgroundMixProportion`、`uBackgroundColor`：线条边缘混合背景色时使用。
- `uUsePrimitiveLines`：当前绘制是否走 primitive line 路径。

同时，bundle 中的 primitive type 明确包含 `PRIMITIVE_LINE`，并且渲染时会用
`parent.getPrimitiveType() === PRIMITIVE_LINE` 设置 `uUsePrimitiveLines`。

这说明 Onshape 不是只把线丢给原生 WebGL `LINES`。它至少存在一条专门的 primitive line 渲染路径。

#### 4. Shader 用 lineStipple 决定 dash / gap

`docs/woolsthorpe.baec8ca135f3f77bba60.js` 中的 fragment shader 可以确认：

- `lineStipple` 是 4 段结构。
- 第 1 段是 dash。
- 第 2 段是 gap。
- 第 3 段是 dash。
- 第 4 段是 gap。
- shader 用 `edgeLength` 对完整 stipple 周期取模。
- 落在 gap 区间的 fragment 会被 discard，或者通过 alpha multiplier 淡出。

也就是说，Onshape 的虚线不是“画很多小线段”的业务逻辑，而是 line distance / edge length 加 shader stipple 规则。
本项目当前 `shaderProgram.ts` 里也有类似的 `lineDistance + lineStipple` 判断，这条方向是对的。
差距在于本项目仍然依赖原生 `LINES`，线宽和边缘质量不可控。

#### 5. Shader / 几何层支持屏幕空间线宽

`docs/woolsthorpe.baec8ca135f3f77bba60.js` 中还可以确认 primitive line 顶点输入和计算逻辑：

- 有 `aEdgeData`，其中包含 edge direction、edge length、corner index、infinite flag。
- 有 `aEdgeLength`，用于在 shader 中计算 stipple 相位。
- 有 `computeTangentAndNormalOffsets(...)`。
- 该函数会把 edge direction 投影到屏幕，再基于 viewport 计算 screen normal。
- shader 会沿切线和法线方向偏移顶点，构造线条 quad。
- `edgeColor(...)` 用 `lineWidth`、`filterDistance` 和 `uLineFilterWidth` 计算透明度 fall-off，实现线边缘抗锯齿。

这说明 Onshape 的高质量线渲染核心不是“原生 lineWidth 调大一点”，而是有 primitive-line / 屏幕空间展开能力。
它把线段作为可带宽度的屏幕空间几何来画，再在 shader 里处理 stipple 和边缘 alpha。

#### 6. 本项目当前差距

本项目当前链路是：

```txt
CanvasEdgeObject
  -> GeometryBufferBuilder.segments()
  -> drawMode: "lines"
  -> WebGLRenderingContext.LINES
  -> a_line_distance + u_line_stipple
  -> fragment discard gap
```

这条链路已经能表达 construction / solid，但还不是 Onshape 那种完整线渲染能力。
差距明确有四个：

- 没有 primitive-line 等价路径。
- 没有 screen-space quad 展开。
- 没有 `uLineFilterWidth` 等价的边缘抗锯齿控制。
- 没有统一管理 width、stipple、filter width、cap、join、depth policy 的 line render style。

所以后续不是继续在 command 里补 helper，也不是继续调某个 dash 数字。
正确方向是先在 `webgl-engine` 收拢 line render style，再实现 primitive-line 等价的屏幕空间线渲染。

#### 7. 对圆心圆弧预览的直接结论

`docs/woolsthorpe.baec8ca135f3f77bba60.js` 中存在用于圆心圆弧第一阶段预览的 `displayProtoArcGraphics` 相关链路。
结合浏览器实测，可以确认：

- 第一阶段 preview circle 是 construction 线。
- 第一阶段 radius preview line 也是 construction 线。
- 第二阶段完整参考圆和 radius preview line 消失。
- 第二阶段只保留 solid arc 预览。

因此文档后续验收标准必须按这个行为写。
其中“construction 怎么显示成虚线”应由线渲染系统负责，不应由圆心圆弧 command 自己决定 dash/gap。

## 当前实现

当前项目已经打通了短期可用的线型语义链路：

```txt
packages/core
  DraftLineStyle = "solid" | "construction"
  DraftLineSegmentObject.lineStyle

packages/canvas
  CanvasLineStyle = "solid" | "construction"
  CanvasEdgeObject.lineStyle

packages/cad-canvas
  DraftRenderAdapter 按 lineStyle 和 color 分组输出 CanvasEdgeObject

packages/webgl-engine
  EdgeStyle.lineStyle
  RenderMaterial.lineStipple
  shader 根据 line distance 和 stipple 丢弃 gap fragment

packages/editor
  SketchCenterPointArcCommand 第一阶段把参考圆和半径参考线标记为 construction
  SketchCenterPointArcCommand 第二阶段只输出 solid 圆弧
```

这条链路的价值是正确的：业务命令表达线的语义，显示层负责具体画法。

当前限制也明确：

- 仍然使用原生 WebGL `LINES`。
- 浏览器和显卡通常无法稳定控制原生线宽。
- 原生线没有可靠的端帽、连接、边缘抗锯齿控制。
- 当前 dash/gap 依赖模型线长乘相机比例，不是真正完整的屏幕空间线渲染。
- hover、selected、preview、model 还没有完全收敛到同一套线渲染模型。

因此当前实现只算阶段 1 的短期实现，不是最终显示架构。

## 概念定义

后续实现必须区分下面几个概念。

### lineStyle

线型语义，表示线本身属于哪种 CAD 线型：

```txt
solid
construction
hidden
center
```

当前只实现：

```txt
solid
construction
```

### lineRole

显示角色，表示这条线来自哪个显示场景：

```txt
model
preview
selection
highlight
```

`lineRole` 不等于 `lineStyle`。

例如：

- 一个 construction preview line：线型是 `construction`，显示角色是 `preview`。
- 一个 selected model edge：线型仍是原业务线型，显示角色是 `selection`。

### interactionState

交互状态，表示对象当前是否被 hover 或 selected：

```txt
normal
hover
selected
```

禁止把 hover/selected 混进 `lineStyle`。它们会影响颜色、线宽、深度策略或高亮层，但不是 CAD 线型本身。

## 包职责与边界

### packages/core

职责：表达 draft 的业务语义。

允许：

- `DraftLineStyle`
- `DraftLineSegmentObject.lineStyle`

禁止：

- dash 数组
- WebGL uniform 名称
- 像素线宽
- shader 常量

依赖变化：不改变。

### packages/canvas

职责：承接 CAD 显示对象到 render graph 的公共 DTO。

后续扩展项：

- `CanvasLineStyle`
- `CanvasLineRole`
- `widthIntent`
- `displayPriority`

这些字段只能表达显示意图，不能表达 WebGL 细节。

依赖变化：不改变。

### packages/cad-canvas

职责：把 draft、sketch display、selection display 转成 canvas scene。

要求：

- 按 `lineStyle`、`lineRole`、color 分组，减少 draw call。
- 不写 dash 数组。
- 不写 shader uniform。
- 不做屏幕空间几何展开。

依赖变化：不改变。

### packages/webgl-engine

职责：实现线条渲染细节。

后续核心能力：

- 统一解析 `lineStyle` / `lineRole` / `interactionState`。
- 统一管理 width、stipple、filter width、cap、join、depth policy。
- 实现屏幕空间线渲染。

依赖变化：不改变。

如果需要新增或修改对外导出 API，编码前必须单独确认。

### packages/editor

职责：根据交互阶段标记线的业务语义。

要求：

- 圆心圆弧第一阶段：参考圆和半径参考线使用 `lineStyle: "construction"`。
- 圆心圆弧第二阶段：真实圆弧预览使用默认 `solid`。

禁止：

- dash pattern
- WebGL 常量
- 线宽像素值
- shader 细节

依赖变化：不改变。

## 分阶段实施计划

### 阶段 1：验收当前线型语义链路

目标：确认当前 `DraftLineStyle -> CanvasLineStyle -> EdgeStyle -> RenderMaterial -> shader` 链路可用，且没有职责越界。

实施内容：

- 保留 `solid` 和 `construction` 两种语义。
- 检查调用点，确保只有参考线设置 `construction`。
- 圆心圆弧第一阶段：参考圆和半径参考线都是 construction。
- 圆心圆弧第二阶段：只显示 solid 圆弧，不显示完整参考圆和半径参考线。

验收：

- `pnpm check` 通过。
- 本地浏览器验证圆心圆弧第一阶段和第二阶段。
- Chrome / Onshape 对照截图确认第一阶段参考圆和半径线均为虚线。

### 阶段 2：收拢 webgl-engine 线型解析

目标：把线型常量和解析逻辑集中在 `webgl-engine` 内部，避免散落在 `renderMaterial.ts`、renderer、shader 绑定逻辑中。

阶段 2 新增内部模块：

```ts
export type EdgeLineStyle = 'solid' | 'construction';

export interface LineRenderStyle {
    readonly widthPx: number;
    readonly stipple: readonly [number, number, number, number];
    readonly filterWidthPx: number;
}

export function resolveLineRenderStyle(style: EdgeLineStyle): LineRenderStyle;
```

规则：

- `solid` 使用连续线。
- `construction` 使用 dash/gap pattern。
- 阶段 2 只收拢规则，不承诺彻底解决原生 `LINES` 的像素稳定问题。
- pattern 的目标单位按屏幕像素设计；在原生 `LINES` 兼容阶段保留现有 line distance scale 近似。
- 如果 `resolveLineRenderStyle` 需要作为 public export，编码前必须确认 public API 变更。

验收：

- 业务包不 import 线型渲染 token。
- 当前圆心圆弧预览视觉不回退。
- `pnpm check` 通过。

### 阶段 3：实现屏幕空间线段几何

目标：停止依赖原生 WebGL line 宽度，改用 primitive-line 等价的 triangle mesh 渲染线条。
这一阶段的目标不是照搬 Onshape 的压缩代码，而是实现同类能力：线段带自己的长度、方向、角点和屏幕空间展开数据。

核心思路：

```txt
输入：
  world-space start / end
  edge direction
  cumulativeDistance
  corner / side flag
  line render style

几何展开：
  每段线生成可展开为屏幕空间 quad 的 4 个角点

shader：
  根据投影后的 edge direction 和 viewport 计算 screen normal
  按 line width 沿 screen normal 偏移顶点
  根据到线中心的距离计算 alpha
  根据 cumulativeDistance 和 stipple 判断 dash/gap
```

和 Onshape bundle 对应的关系：

- `aEdgeData` 对应本项目后续需要新增的 line geometry attribute。
- `aEdgeLength` 对应本项目已有的 `line-distance`，但阶段 3 需要保证它在曲线连续段中稳定累计。
- `uLineFilterWidth` 对应本项目后续需要新增的抗锯齿 fall-off uniform。
- `PRIMITIVE_LINE` 对应本项目后续的 styled line draw path，不能继续直接走原生 `LINES`。

需要支持：

- 固定屏幕像素线宽。
- 固定屏幕像素 dash/gap。
- 端点 cap。
- 曲线采样段连续共享 dash 相位。
- 非连续 segment 不共享 dash 相位。
- 在透视和正交相机下都按屏幕空间宽度显示。

本阶段暂不做：

- 不做动态尺寸文本。
- 不做约束显示。
- 不做 selection picking 语义重写；pick 仍然基于原业务对象。
- 不支持 infinite line，除非后续工具明确需要。

验收：

- construction 圆虚线在缩放时 dash 长度稳定。
- 第一阶段半径参考线保持 construction 虚线。
- 第二阶段圆弧保持 solid 实线。
- 线条边缘不再依赖原生 `LINES` 的默认锯齿效果。
- `pnpm check` 通过。

### 阶段 4：替换 styled edge 渲染路径

目标：让普通 edge、draft edge、preview edge 走统一屏幕空间线渲染。

实施内容：

- `CanvasEdgeObject` 仍表达业务显示对象，不直接进入原生 line buffer。
- `webgl-engine` 根据 line style / role / state 解析最终 line render style。
- 原生 `LINES` 只保留为临时兼容路径，最终移除。

验收：

- line、rectangle、circle、three point circle、ellipse、three point arc、center point arc 都正常显示。
- 删除、undo、redo 不受影响。
- `pnpm check` 通过。

### 阶段 5：统一 selection / highlight 线条显示

目标：hover、highlight、selected 不再拥有独立且不一致的线条渲染逻辑。

实施内容：

- hover/selected 通过 lineRole 或 interactionState 影响最终显示。
- hover/selected 不混入 lineStyle。
- 曲线仍以原始业务 curve 为选择对象，不暴露采样 segment。

验收：

- 曲线 hover 是整条曲线高亮。
- 曲线 selected 是整条曲线选中。
- 点击空白后取消选择。
- Delete/Undo/Redo 行为不退化。
- `pnpm check` 通过。

当前实现记录：

- `HighlightPass` 不再自己手写草图 thick-line 的 clip/screen/NDC 转换。
- hover / preselect / selected 的 edge 高亮统一生成 `LineSegment3` batch，再走 `screenSpaceLineSegments()`。
- 草图 edge 高亮仍保持 overlay 显示状态和 3px 线宽；普通 scene edge / face boundary 高亮仍保持深度测试。
- `lineStyle` 仍只表达业务线型，hover / selected 没有混入 `lineStyle`。
- 曲线仍按原业务 curve 对象选择，不暴露采样 segment。

### 阶段 6：圆心圆弧预览最终对齐

目标：以 Onshape 圆心圆弧两个阶段作为验收基准。

验收场景：

- 第一阶段：完整 construction 参考圆，dash 分布稳定。
- 第一阶段：半径参考线也是 construction 虚线。
- 第一阶段：显示圆心点和当前半径点。
- 第二阶段：完整参考圆消失。
- 第二阶段：半径参考线消失。
- 第二阶段：只显示 solid 圆弧。
- 第二阶段：显示圆心、起点、终点相关点标记。
- 不把动态尺寸文本作为本阶段要求。
- 本地截图与 Onshape 截图并排确认。
- `pnpm check` 通过。

当前本地验收记录：

- 本地第一阶段显示完整 construction 参考圆。
- 本地第一阶段半径参考线显示为 construction 虚线。
- 本地第一阶段显示圆心点和当前半径点。
- 本地第一阶段滚轮缩放后，参考圆和半径线仍保持 construction 虚线。
- 本地第二阶段完整参考圆消失。
- 本地第二阶段半径参考线消失。

## 风险点

- 深度排序：preview、model、selection、highlight 的绘制顺序必须稳定。
- picking：线宽变粗后，拾取语义仍应基于业务对象，不能变成采样 segment。
- 性能：曲线采样后展开为 quad 会增加顶点数，需要批处理和材质分组。
- DPI：`devicePixelRatio`、浏览器缩放、相机投影会影响屏幕像素换算，必须统一入口。
- join/cap：圆、圆弧、折线、矩形需要不同连接处理，不能只做单段 quad。
- public API：涉及 `canvas`、`webgl-engine`、`core` 的对外类型或导出变更时，必须先做包职责与改动边界确认。

## 当前结论

当前未提交实现已经完成阶段 1 到阶段 6 的目标：

- 阶段 1：草图线型语义链路已验收，`construction` 能从 editor 传到 `webgl-engine`。
- 阶段 2：`webgl-engine` 内部已集中解析 `solid` / `construction` 的线型渲染参数。
- 阶段 3：普通 edge / draft edge / preview edge 已具备屏幕空间线段几何能力，不再依赖原生 WebGL line 宽度。
- 阶段 4：`RenderableObjectBuilder.edges()` 和 `RenderableObjectBuilder.lines()` 已统一走屏幕空间线段几何；原生 `LINES` 仍保留给 navigation depth、view cube 和 immediate primitive 兼容路径。
- 阶段 5：hover / preselect / selected 的 edge 高亮已收敛到屏幕空间线段几何；原生 `LINES` 不再用于 highlight edge。
